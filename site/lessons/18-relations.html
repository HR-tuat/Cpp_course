クラス間の相互参照

互いを知りたいクラスを、壊れない形で書く。

互いを知りたくなる場面

クラスが増えると、必ずこの形にぶつかる。RobotはControllerを部品として持っている。一方Controllerは、判断のためにRobot全体の状態を知りたい。

素直に書くと、両方のヘッダが相手を#includeすることになる。

両方includeすると何が起きるか

#pragma onceがあるので無限に展開されることはない。代わりに「片方が先に読まれ、もう片方はまだ存在しない」という状態でコンパイルが進む。

このエラーは「includeを足せば直る」ように見えるため、足した結果さらに循環が深くなることが多い。include を増やす方向では解けない。

前方宣言

解決は逆方向である。Controllerが本当に必要なのは「Robotというクラスが存在する」という事実だけで、中身ではない。それだけを伝えるのが前方宣言である。

#include "Robot.hpp"が消えたので、循環が切れる。Robot.hpp側は今までどおり#include "Controller.hpp"してよい。

前方宣言でできること・できないこと

前方宣言されただけの型を不完全型という。大きさも中身も分からないので、できることは限られる。

書き方理由
Robot* robot;○ポインタの大きさは相手に依らない
Robot& robot;○同じ
void f(Robot& r);の宣言○宣言するだけなら中身は不要
Robot robot;×何バイト必要か分からない
robot.update();×そのメンバがあるか分からない
class X : public Robot×親の中身が分からない

ポイント

「ヘッダでは相手を指すだけ、中身を触るのは.cpp」と覚える。これは循環を避ける以外にも効く。ヘッダのincludeが減るぶん、相手のヘッダを直したときに再コンパイルされる範囲が狭くなる。

中身を使うのは.cppで

.cppは誰からもincludeされないので、ここで#include "Robot.hpp"しても循環は起きない。

所有関係を決める

相互参照を書く前に決めなければならないことがある。どちらが相手を所有しているかである。両方が所有するように書くと、どちらが先に消えるのか決まらなくなる。

向き関係書き方
Robot → Controller所有する（親→子）値のメンバ、またはstd::unique_ptr
Controller → Robot参照するだけ（子→親）Robot& または Robot*

注意

コンストラクタの初期化リストで*thisを渡せるのは、相手がその場で自分のメンバを使わない場合に限られる。Controllerのコンストラクタがrobot.isObstacleAhead()を呼ぶと、Robotのメンバがまだ初期化されていない状態で読むことになる。渡した参照は保存するだけにして、使うのはupdate()からにする。

shared_ptrで双方向に持つと解放されない

第17回のshared_ptrを、双方向にそのまま使うと静かにリークする。

これを循環参照という。解決は所有関係のとおりに型を選ぶこと、つまり子から親への向きをweak_ptrにすることである。

補足

マイコンでは、そもそもRobotをグローバルやメンバとして静的に置くことが多い。その場合shared_ptrは登場せず、子はRobot&を持つだけで済む。循環参照はshared_ptrを双方向に使ったときにだけ起きる問題である。

そもそも相互参照を減らす

前方宣言は相互参照を書けるようにする道具であって、相互参照を良いものにする道具ではない。互いを知っているクラスは片方だけを切り出して読むことができず、テストもしにくい。まず依存の向きを一方向に揃えられないかを考える。

案1：必要な情報だけ引数で渡す

ControllerからRobotへの参照が消え、Controller単体で動作を確かめられるようになる。相互参照の多くは、本当は「相手の一部が欲しいだけ」である。

案2：抽象クラスで向きを変える

どうしても相手に問い合わせたい場合は、第12回の抽象クラスを挟んで、依存の向きを変える。

ControllerはRobotを知らなくなり、別のクラスを渡してテストできるようになる。

判断の順番

  1. 本当に相手全体が必要か。必要な値を引数で渡せないか
  2. 渡せないなら、抽象クラスを挟んで向きを一方向にできないか
  3. それでも相互に必要なら、前方宣言で書く。所有は片方だけに持たせる

講師向け

この回は先にエラーを出させるのが早い。互いに#includeしたヘッダを配り、コンパイルさせてhas not been declaredを見せる。そこから「ControllerはRobotの何を知りたいのか」を問うと、案1（引数で渡す）に自然に辿り着く受講者が出る。前方宣言はその後に出すほうが定着する。code/final-projectのControllerがMotor&とDistanceSensor&だけを受け取っていてRobotを知らない点も、実例として示せる。

動かして確かめる

演習に入る前に、まずこのサンプルを動かして結果を見る。追加の部品は要らない。光るのはボードに載っている内蔵LEDで、それ以外はシリアルモニタの出力で確かめられる。code/examples/18-relations/を開き、pio run -t uploadで書き込んでからpio device monitorで出力を見る（手順と、外付けのLEDなどをつなぐ場合は開発環境にまとめてある）。

確かめること。

  • Controller.hppに#include "Robot.hpp"がない。class Robot;の1行で足りている
  • Controller.hppの前方宣言を#include "Robot.hpp"に書き換えるとビルドが止まり、'Robot' does not name a typeと出る。一度自分で出しておく
  • 距離が150mmを切ったところでobstacle -> stopに変わる。判断はController、状態はRobotが持っている
  • Controllerのコンストラクタでrobot.isObstacleAhead()を呼ぶと何が起きるかを考える（Robotのメンバはまだ初期化されていない）
  • ControllerがRobotから取っているのは「障害物があるか」だけ。引数で渡す形にすれば相互参照が消せないかを考える

演習：RobotとControllerの相互参照を解く

  • Robot.hppとController.hppが互いを#includeするコードを書き、出るエラーを読む
  • Controller.hppを前方宣言に直し、Controller.cppでRobot.hppをincludeして通す
  • 所有はRobot側だけに持たせ、ControllerはRobot&を保存するだけにする
